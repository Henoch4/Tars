# TARS — Open Design Decisions: Resolutions
**Reviewer:** independent review (per request in `Open Design Decisions —TARS.md`, 2026-08-28)
**Basis:** repo inspection (`src/multi_leg.py`, `src/execution/risk_gate.py`,`src/audit_logger.py`, `src/curator.py`, `src/vault_api.py`) plus the statedglobal constraints (tests locked, fail-closed bias, dry-run zero-side-effect,honesty invariant, regression rule, `t3n/` scope guard).Each decision below states: **the ruling**, why, and what it implies for theimplementer. Where a decision splits into "now" and "before live capital,"that split is deliberate — this system is explicitly not live-capital readyyet, so the two bars are different.---## D1 — Multi-leg partial-fill accounting → **(b) now, (a) before live multi-leg**Adopt **(b)** immediately: any live multi-leg package aborts outright themoment a leg lands `PARTIALLY_FILLED`, and the abort unwinds the *other* legsat their actual filled amounts (not notional). This is a pure tightening —it can only reject packages that today would silently mis-hedge — so it'ssafe to ship without waiting on the bigger redesign.**(a) is approved as the target design** and should be scheduled beforemulti-leg is ever pointed at live capital. The amount-aware unwind spec aswritten is approved as the contract: per-leg fill ratios threaded through`LegResult`, unwinds scaled to the filled amount of the broken leg (notnotional), <99.9% fill treated as a breach. This is the only version of thefeature that's actually safe to run unattended, so it shouldn't ship as a"nice to have" later — it's a precondition for multi-leg going live, not anenhancement to it.Do not ship (c) — restricting to market-order legs to keep fill_prob ~1doesn't eliminate partial fills (market orders partially fill on thin bookstoo), it just makes them rarer and therefore *less tested* when they happen.---## D2 — Kill-switch durability → **(a) now, (b) mandatory gate before live**Matches the review's own recommendation, and it's the right call. Persistswitch state (`active`, `reason`, `activated_at`) into the same`DurableDailyCounters` JSON store — cheap, reuses an already-trustedmechanism, closes the restart gap for the common case.For live mode specifically, `sync_with_onchain` at boot becomes **mandatory**,not optional: if reconciliation can't run, the process refuses to traderather than starting in an unknown kill-switch state. This is a straightapplication of the fail-closed constraint — "kill switch state unknown" ismissing/malformed input by another name.Local JSON durability is a legitimate interim state for paper/testnet; it isnot sufficient on its own once real capital is at risk, because it can'tsurvive disk loss/corruption the way the onchain record can.---## D3 — Fat-finger check for market orders → **(a)**, threshold = `max_slippage_pct`Ship (a): add `intended_price` to `OrderRequest`, populated from the signalgeneration stage's mid/last price, and reject pre-trade if it deviates morethan the threshold from the fresh reference price used by check 9. Reuse`max_slippage_pct` as the threshold rather than inventing a second number —the two checks are conceptually the same guardrail (agent's view of price vs.reality) applied at two different moments, and a second free parameter wouldjust be another thing to get out of sync.Reject (c): making market orders conditional on `entry_price` existingquietly changes execution behavior based on an unrelated field's presence,which is exactly the kind of implicit coupling the honesty invariant ismeant to prevent. If the intent is "don't trade on stale/absent signalprice," say that directly as its own check, not as a side effect of theorder-type branch.(b) — post-trade only — is the status quo and is the reason this decisionexists; not selecting it.---## D4 — Volume limit → **(a) enforce**, independent capEnforce it. A control that's tracked but not gated, with docs implyingotherwise, is a direct honesty-invariant violation as currently shipped —this isn't really optional given the stated constraints.`max_daily_volume` sits as an **independent gate**, not folded into thetrade-count quota: reject when `(day volume + order notional) >max_daily_volume`, checked separately from and in addition to the countcheck. Volume and count bound different failure modes (many smallmispriced orders vs. one huge one); collapsing them into a single gate wouldlet a strategy trade the full volume budget in one order without tripping acount-based expectation, or vice versa.---## D5 — Allowlist semantics → **(a) exact match + explicit companion list**Go with (a). The system's entire premise is that what the agent is permittedto trade is a deliberate, auditable operator decision — base-asset familymatching means an operator who allowlists `BTC-USDT-SWAP` has, withoutrealizing it, also allowlisted every dated BTC future that exists or willexist. That's a materially different risk surface than "the spot leg forfunding-arb," which is the only case the docstring actually claims tosupport.Declare the funding-arb spot leg (and any similar companion legs) explicitlyin config, matched exactly by the gate. This is more operator overhead than(b), but it's the only option where the allowlist means what it says — whichmatters more here than in a typical system, because the allowlist is asafety control, not a convenience feature. (c) is rejected outright: fixingthe docstring to match a behavior nobody asked for isn't a resolution, it'sdocumenting the bug.
---## D6 — audit_logger hardening → **approve all three as one batch**All three are low-risk, behavior-preserving-for-integral-values, and each oneindividually closes a real honesty/correctness gap in the audit trail — whichis the system's core claim ("written first"). No reason to split them:- **1a** (`Decimal`-based fixed-point conversion): fixes a forensic mismatch  that would otherwise surface exactly when it's least convenient — during  an independent audit recomputing from decimal strings.- **2a** (re-read chain nonce on failover/reorg, WARN on divergence): closes  a silent-divergence path with a logged signal instead of nothing.- **3a** (measure actual block time once at construction): replaces an  unverified assumption (15s blocks / 5760 per day) with a measured value,  which matters for any day-window math (durable counters, volume caps) that  depends on it being right.Ship together; none of the three depends on a product judgment call, they'recorrectness fixes.---## D7 — Curator auto-revert behavior → **(a)**Trailing-window PnL for the revert trigger, and **no automatic revert out offorced-defective** — that transition requires a manual operator action.Reasoning: the review is right that the curator is advisory, not the safetylayer — the risk gate is. But "advisory" doesn't mean "consequence-free."`defensive` is a state the system enters *because* something went wrong;letting it auto-revert to `previous_profile` — which can be the very profilethat caused the drawdown — creates a ping-pong that a human would obviouslynever approve if asked directly. That's a low-cost fix (gate a statetransition on an operator action) for a real tail risk, so it's worth doingeven though the curator sits one layer below the hard safety boundary.Cumulative PnL masking later losses behind one early win is a separate bugin the same function and gets fixed by the same trailing-window change.`_apply_switch`'s ignored `forced` parameter should be wired to actuallygate the auto-revert path (`forced=True` states don't auto-revert) ratherthan left as accepted-but-inert — an ignored parameter that looks load-bearingis itself an honesty-invariant issue.---## D8 — vault_api latency hardening → **(c) cap + paginate now, document the cap**Cap `count` at ~20 with pagination for anything beyond that, and document thelimit in the endpoint's docstring/API notes. This directly bounds theworst case (100 sequential RPC calls pinning a worker for minutes) with theleast new surface area, and is proportionate to "single-operator API" as itexists today.TTL caching (a) and async/gather batching (b) are legitimate futureupgrades if usage patterns change (multiple operators, dashboards pollingfrequently) — not needed to close today's actual failure mode, so hold themrather than building ahead of demonstrated need.---## D9 — Hygiene batch → **approve as a batch**, with one addition to item 6Approve items 1–5 as written. For item 6 (dead-code policy), the ruling is:- **Keep** anything referenced by scripts or tests (`get_nonce()`,  `fill_timeout_cycles`), but add a one-line comment at each definition  saying what still uses it — an unexplained "used elsewhere" is exactly the  kind of that gets deleted by accident six months from now.- **Strip** the zero-address fallback in `agent.py` unless there's a  documented state (e.g., a specific dry-run/demo mode) that actually  requires it — if it's a fallback for a case that can't currently occur,  it's dead code wearing a safety-code costume, which is worse than  ordinary dead code because it looks load-bearing.This keeps the hygiene batch aligned with the honesty invariant: nothingsurvives in the repo implying it does something it doesn't.---## Summary table| # | Decision | Ruling ||---|----------|--------|| 1 | Partial-fill accounting | (b) now, ship (a) before live multi-leg || 2 | Kill-switch durability | (a) now, (b) mandatory before live || 3 | Fat-finger on market orders | (a), threshold = `max_slippage_pct` || 4 | Volume limit | (a) enforce, independent gate || 5 | Allowlist semantics | (a) exact match + explicit companions || 6 | audit_logger hardening | approve all three (1a, 2a, 3a) || 7 | Curator auto-revert | (a) trailing window + no auto-revert from forced-defective || 8 | vault_api latency | (c) cap + paginate, document limit || 9 | Hygiene batch | approve, with comment requirement on kept dead code |All rulings assume the global constraints stand unmodified: tests are alocked zone (any conflict with pinned behavior comes back to a human beforeimplementation), every fix gets a regression test, and dry-run stayszero-side-effect throughout.
